# 로그인 시스템(인증 백엔드) 연결

화면만 있는 가입 프로토타입을 실제 인증 서비스에 붙인다. 화면 설계는 `ux-signup-redesign`이 맡고, 이 스킬은 **서버 쪽 구조·보안 규칙·검증 순서**를 맡는다. 본문은 서비스와 무관하게 쓰고, 서비스별 내용은 `providers/` 문서에 둔다. 응답·문서·커밋 메시지는 한국어.

- 서비스별 상세: [providers/supabase.md](providers/supabase.md) (이 저장소에서 실제로 연결한 방식)
- 새 서비스를 붙일 때: 아래 "4. 서비스 매핑"을 채워 `providers/<서비스>.md`를 추가하고 이 파일의 목록에 한 줄 올린다.

## 0. 시작 전에 확인할 것

1. **서비스 선택**: 사용자가 정했는지 확인한다. 정하지 않았으면 1~2개를 비교해 추천한다. 기준은 아래 둘이다.
   - 이메일 **6자리 코드(OTP)** 인증을 지원하는가. 지원하지 않으면 화면을 링크 방식으로 바꿔야 하므로 먼저 사용자에게 알린다.
   - **메일 템플릿**을 고칠 수 있는가, 그러려면 별도 메일 발송 설정(SMTP)이 필요한가.
2. **화면 요구**: 가입 단계(어떤 정보를 받는가), 필수·선택 약관, 인증 방식, 재설정 방식. 받는 정보가 곧 DB 컬럼이 되므로 **연결 전에** 확정한다. 나중에 바꾸면 표와 코드를 둘 다 고쳐야 한다.
3. **사용자가 직접 해야 하는 일**: 서비스 계정·프로젝트 만들기, 메일 서비스 가입과 키 발급. 에이전트가 대신할 수 없다.

## 1. 반드시 지킬 안전 규칙

- 프런트에는 **공개용 키만** 넣는다(예: publishable/anon). 비밀 키(secret, service_role), DB 비밀번호, 메일 서비스 API 키는 코드·문서·커밋·채팅 어디에도 쓰지 않는다.
- 사용자가 비밀 값을 채팅에 붙여 넣었다면 이미 노출된 것으로 보고, 저장하지 말고, 해당 값을 **재발급(재설정)** 하라고 알린다. 파일에 들어갔는지 검색해 확인한다.
- **가입·로그인처럼 암호를 입력하는 테스트는 사용자가 직접** 한다. 에이전트는 서버 로그와 대시보드를 **읽기만 해서** 결과를 확인한다.
- 서비스 대시보드 설정(메일 템플릿, 인증 옵션)을 바꾸려면 사용자의 동의를 먼저 받는다. 바꾼 뒤에는 새로고침해서 저장됐는지 확인한다. 사용자가 시키지 않은 설정은 읽기만 한다.
- 이미 올라간 커밋·브랜치를 고치려면(강제 덮어쓰기) 먼저 묻는다.

## 2. 구조: 화면 코드와 서버 코드를 분리

화면 이벤트 코드가 서비스 SDK를 직접 부르지 않게, 얇은 **API 계층**(어댑터) 하나를 둔다. 서비스를 바꿔도 이 계층만 고친다. 모든 함수는 `{ok:true,...}` 또는 `{error:{code,message}}` 모양으로 돌려준다(예외를 던지지 않는다).

| 함수 | 하는 일 |
| --- | --- |
| `signUp(email, pw, data)` | 계정 생성 + 입력값(이름·약관 등)을 함께 저장, 인증 코드 메일 발송. 이미 가입한 이메일이면 `{exists:true}` |
| `resend(email)` | 인증 코드 다시 발송 |
| `verify(email, code)` | 코드 확인 → 성공하면 로그인 상태 |
| `signIn(email, pw)` | 로그인 |
| `signOut()` | 로그아웃 |
| `resetSend(email)` | 재설정 코드 발송 (가입 여부와 상관없이 성공 응답) |
| `resetDo(email, code, newPw)` | 코드 확인 + 새 암호 설정, 바로 로그인 |
| 세션 복원 | 새로고침해도 로그인 유지 (서비스 SDK가 저장한 세션을 시작 시 읽는다) |

- **미리보기 모드**: 주소에 `?demo`가 있으면 어댑터가 서버를 부르지 않고 가짜 성공을 돌려준다(코드는 `123456`). UX 노트 페이지의 "이 화면 보기" 링크용이다. 실수로 실제 계정·메일이 만들어지는 것을 막는다.
- **오류 문구 매핑 함수**(`authMsg`) 하나로 서버 오류 코드를 한국어 문구로 바꾼다: 요청 한도, 잘못된 로그인 정보, 이메일 미인증, 약한 암호, 같은 암호, 코드 불일치·만료, 네트워크 오류, 그 밖.

## 3. 흐름 설계 규칙

**가입**: 1단계(기본 정보) → 2단계(이메일·암호) → 3단계(약관) → 4단계(코드 입력). **3단계 동의를 마치고 4단계에 들어올 때** 계정을 만들고 메일을 보낸다. 약관 동의 값을 저장해야 하기 때문이다. 4단계에서는 "코드를 보내는 중…"을 보여 준다.
- 가입이 실패하면 4단계에 남아 오류를 보여 주고 "코드 다시 보내기"가 가입부터 다시 시도하게 한다.
- 이메일을 바꾸러 2단계로 갔다 오면 새 이메일로 다시 가입한다. 응답이 늦게 도착해도 **현재 이메일과 다르면 버린다**.

**코드 입력**: 6칸, 자동 이동·붙여넣기, 6자리 완성 시 자동 확인. 5번 틀리면 잠그고 새 코드를 받게 한다. 네트워크·요청 한도 오류는 시도 횟수에 넣지 않는다. 재전송 간격은 **서버의 최소 간격에 맞춘다**(어기면 요청 한도 오류).

**로그인**: 이메일 → 암호 2단계. 이메일 단계에서 가입 여부를 확인하지 않는다. 실패 문구는 "이메일 또는 암호가 맞지 않아요"로 **통일**한다(어느 쪽이 틀렸는지 알려 주지 않음). 5회 실패하면 재설정으로 안내한다. 이메일 미인증이면 가입을 이어서 하도록 안내한다.

**암호 재설정**: 코드 방식이면 한 화면에서 코드 + 새 암호를 받는다. "가입한 계정이 있다면 코드를 보냈어요"로 가입 여부를 숨긴다. 성공하면 바로 로그인한다.

**이미 가입한 이메일**: 서비스가 오류 없이 "성공"처럼 응답하고 응답 모양으로만 구분되는 경우가 많다(Supabase는 `identities`가 빈 배열). 가입 화면에서는 이를 감지해 2단계로 돌려보내 "이미 가입된 이메일"을 알려 주되, **로그인·재설정에서는 존재 여부를 알려 주지 않는다**. 이 절충을 문서에 적어 둔다.

**로그인 상태**: 서비스가 관리하는 세션만 믿는다. 이름 같은 표시용 값은 계정의 사용자 메타데이터에서 읽고, `sessionStorage` 등에 로그인 여부를 따로 저장하지 않는다. 입력 초안은 저장하되 **암호는 저장하지 않는다**.

**서버에 없는 기능은 화면 시연용임을 밝힌다**: 예를 들어 "탈퇴 후 재가입 제한"은 서버에 탈퇴 이력이 없으면 체험 계정에만 반응하는 가짜 규칙이다. README와 코드 주석에 그렇게 적는다. 동작하지 않는 버튼(패스키, 로그인 유지 등)은 지우거나 "준비 중"으로 둔다. 가짜 성공을 보여 주지 않는다.

## 4. 서비스 매핑 (새 서비스를 붙일 때 채울 표)

`providers/<서비스>.md`에 아래를 모두 적는다. 한 칸이라도 비면 아직 연결할 수 없다는 뜻이다.

| 항목 | 적을 것 |
| --- | --- |
| 공개 키·주소 | 프런트에 넣어도 되는 값과 위치, 넣으면 안 되는 값 |
| 8개 어댑터 함수 | 각각 어떤 SDK 호출로 구현하는지, 성공·실패 응답 모양 |
| 사용자 데이터 | 이름·약관 같은 추가 정보를 어디에 저장하는지(메타데이터, 별도 표), 가입 시 자동 저장 방법 |
| 접근 제어 | 본인 데이터만 읽고 고치게 하는 규칙, 필수 약관 위·변조 방지 |
| 이메일 코드 | 코드 길이·만료 시간 설정 위치, 메일 템플릿 수정 조건, 메일 발송(SMTP) 요건·한도 |
| 오류 코드 | 3의 `authMsg`에 매핑할 코드 목록 |
| 이메일 중복 | 이미 가입한 이메일일 때의 응답 모양 |
| 로그 확인 | 요청이 서버에 닿았는지, 메일이 나갔는지 보는 위치 |
| 함정 | 처음 보면 막히는 설정·기본값 |

## 5. 작업 순서

1. 0의 확인을 마친다. 서비스 계정·프로젝트는 사용자가 만든다.
2. **서버 설정과 SQL(또는 규칙)을 파일로 먼저 쓴다**(예: `supabase/schema.sql`). 사용자가 실행하기 전에는 "작성했을 뿐 실제로 돌려 보지 못했다"고 말한다.
3. 메일 설정(템플릿, 코드 길이, 발송 설정)은 서비스 문서에 따라 맞춘다. 사용자가 해야 하는 부분은 단계별 안내와 바로 가기 링크를 준다.
4. 프런트에 어댑터와 흐름을 넣고, 기존 가짜 코드(가짜 계정, 고정 코드, 가짜 중복 조회)를 **남김없이 지운다**. 지운 뒤 잔재를 검색한다.
5. **서버 없이 확인**: 문법 검사, `?demo` 흐름, 가짜 계정으로 로그인해 **서버가 거부 응답을 주는지**(키·주소가 맞다는 증거, 계정이 만들어지지 않음).
6. **사용자가 직접 실제 시험**: 가입 → 코드 입력 → 로그인 → 새로고침 유지 → 로그아웃 → 암호 재설정 → 이미 가입한 이메일로 재가입. 순서와 확인 방법을 번호 목록으로 안내한다.
7. 시험 뒤 에이전트가 **읽기만** 한다: 사용자 목록, 프로필 표의 값, 인증 로그. 값이 기대와 다르면(예: 국가가 코드가 아니라 화면 문구로 저장) 문서를 실제에 맞춘다.
8. README·UX 노트·서비스 문서를 갱신한다. 문서의 시간 값(재전송 간격 등)을 코드와 맞춘다.

## 6. 자주 막히는 문제와 확인 순서

| 증상 | 먼저 볼 곳 |
| --- | --- |
| 메일이 안 온다 | ① 서버 로그에 요청이 있는지(없으면 가입을 아직 안 한 것) ② 사용자 상세에 발송 기록이 있는지 ③ 입력한 이메일이 가입한 이메일과 같은지(재설정은 오타여도 성공 응답) ④ 스팸함 ⑤ 메일 서비스의 발송 상태 ⑥ 발송 한도 |
| 코드 칸 수와 메일의 코드 길이가 다르다 | 서버의 코드 길이 설정 |
| 템플릿이 수정되지 않는다 | 서비스의 조건(예: 커스텀 SMTP 필요) 안내 문구 |
| 로그인이 "인증 안 됨" | 이메일 인증을 마쳤는지 |
| 테스트에서 포커스·blur 이벤트가 안 일어난다 | 브라우저 자동화에서는 `blur()`가 이벤트를 못 내므로 `dispatchEvent`로 직접 발생시킨다 |
| 같은 주소에서 해시만 바꿔 열면 스크립트가 다시 안 돈다 | 쿼리 문자열을 바꾸거나 새로 불러온다 |

## 7. 답변

짧게: 무엇이 연결됐는지, **실제로 확인한 것과 확인하지 못한 것**(특히 실제 메일 발송), 사용자가 직접 할 일 한 가지, 다음 한 단계. 비밀 값이 노출됐다면 재발급을 권한다. 이미 가입 여부가 가입 화면에 드러나는 것 같은 절충은 숨기지 말고 알린다.
